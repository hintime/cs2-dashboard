# sense-skin-ai 的 AI 决策是怎么做的（源码拆解）

> 仓库：github.com/yangkaiwen2002/sense-skin-ai（本地已克隆到 `C:\Users\Lenovo\sense-skin-ai`）
> 核心文件：`backend/app/services/scoring.py`（7 维评分）、`decision_engine.py`（决策）、
> `event_mapper.py`（事件映射）、`opportunity_detector.py`（机会扫描）、`app/rag/`（知识库检索）

## 一句话总结

**它的"AI 决策"里根本没有 LLM。** 决策是纯确定性规则：7 维加权评分 → 6 类证据计分（±分）→
净分映射到 BUY/WATCH/HOLD/AVOID 四档。LLM 只用在两处边缘：RAG 知识库问答、报告润色。
它 README 里那句 "AI as a system component, not the whole product" 是准确的。

## 1. 七维评分（0-100 加权和）

| 维度 | 权重 | 怎么算的 |
|---|---|---|
| 稀有度 Rarity | 18% | **静态字典**：违禁/隐秘/保密/受限…→固定分，缺省 40 |
| 外观 Exterior | 12% | **静态字典**：崭新≈95 / 略磨≈80 / 久经≈55… |
| 流动性 Liquidity | 18% | 近 7 日均成交量 + 挂单深度 + spread 的组合函数 |
| 趋势 Trend | 14% | `50 + 7日涨跌幅×800`（涨 1% = +8 分，截断 0-100）|
| 估值 Valuation | 14% | `50 + (30日均价−现价)/30日均价×400`（低于均价 12.5% = 满分）|
| 需求 Demand | 12% | `武器类别基础分 + (稀有度−40)×0.2 + StatTrak +10` |
| 事件 Event | 12% | `50 + 事件影响分×40`（见下）|

- 估值标签：估值分 ≥65 →「低估」，40-65 →「合理」，<40 →「高估」
- 置信度：`0.38 + 0.32×数据覆盖率 + 0.20×流动性因子 + 0.05×有事件`（诚实的不确定性）
- reasons/risks：按每个维度的阈值生成 2-3 档文案（和我们 `_reason` 的思路一样）

## 2. 决策引擎：证据计分（不是 LLM）

6 类证据各自加分/减分，**全部写进 evidence_log（可审计、可复现）**：

| 证据 | 分值 |
|---|---|
| 估值：低估 +2 / 高估 −2 | ±2.0 |
| 趋势：≥68 +1.5，≥55 +0.5，≤33 −1.5 | ±1.5 |
| 事件影响：≥0.45 +2，≥0.20 +1，≤−0.35 −2，≤−0.15 −1 | ±2.0 |
| 流动性：≥65 +1，≤30 −1 | ±1.0 |
| 总分档：≥74 +2，≥62 +1，≤40 −2 | ±2.0 |
| 风险标签：每条 −0.5（最多 3 条） | −1.5 |

**阈值映射**（双重门槛：既要净分够、又要总分够）：

```
net ≥ +3.0 且 total ≥ 62  →  BUY   （置信度 = 0.55 + net×0.06 + total×0.002，封顶 0.93）
net ≥ +1.0 且 total ≥ 52  →  WATCH
net ≥ −1.0 且 total ≥ 42  →  HOLD
否则                      →  AVOID
```

同时输出 `upside_factors`（最多 5 条）、`risk_factors`（3 条）、`score_summary`（7 维分数）。

## 3. 事件映射（最有借鉴价值的部分）

事件库存于 `data/events.json`（赛事/更新/季节活动，含方向、强度 0-1、置信度、来源）。

```
相关度 relevance = 品类匹配 × 时效权重 × 事件强度 × 事件置信度

品类匹配：  具体饰品 1.0 ＞ 武器类型 0.9 ＞ 稀有度档 0.8 ＞ StatTrak 0.75 ＞ 全部 1.0(缺省)
时效权重（手工调的时段表）：
    未来 14-30 天 = 0.60
    未来  7-14 天 = 1.00   ← 赛前黄金窗口（还没被炒到顶）
    未来  0-7  天 = 0.90   ← 已被提前定价
    过去  0-7  天 = 1.00   ← 赛后峰值
    过去  7-30 天 = 0.55
    过去 60-90 天 = 0.10
    窗口外 = 0
event_impact = Σ(相关度 × 方向符号)，截断 [-1, +1]
```

事件由 `event_ingestion.py` 从 HLTV 等来源抓取/整理，`opportunity_detector.py` 跑全库输出机会卡。

## 4. RAG 知识库（LLM 的唯一深度参与）

知识库仅 32 条人工整理条目（稀有度定价/磨损影响/赛事效应/平台差异/租 vs 买/StatTrak 溢价）。
检索是**三引擎融合**：FAISS 语义（多语言 MiniLM）+ BM25（中文用字符 bigram）+ TF-IDF（字符 n-gram），
按加权 RRF 融合排序。用户提问时，检索到的条目作为 grounding 塞进 prompt，让 Claude 只基于知识库作答。

## 5. 对照我们的项目：能抄什么、不用抄什么

**值得抄（按性价比）**：
1. **证据计分决策**：把我们的 `_reason` 文本拼接升级成 `evidence_log` 结构化数组 + 净分 + 四档判定。
   我们已有全部信号源（估值=compre vs price、趋势=rate_7/30、流动性=在售量、综合分、新闻影响），
   落地成本大概半天，收益是**每条推荐可审计、可复现**，前端还能画出"为什么"。
2. **事件时段表**：把我们的「赛事贴纸」洞察量化。现在已经能拿到赛事新闻，缺的就是这张
   时段权重表 + 品类匹配（贴纸→对应战队/赛事 → 相关度）。
3. **置信度公式**：`数据覆盖率 + 流动性 + 有无事件` 三因子，比我们现在裸的"置信度 80"诚实。

**不用抄**：
- 静态稀有度/外观字典（我们没有这个数据源，硬编字典=编数据）
- RAG 三引擎（faiss + sentence-transformers 重依赖，且我们的知识面已由市场新闻+AI 洞察覆盖）
- PostgreSQL/SQLAlchemy 全家桶（我们的 SQLite + 静态站架构更省）
